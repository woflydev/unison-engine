# Unison UI constitution

Binding for every agent and contributor touching UI. It covers how the app looks and feels; where code lives is `docs/ARCHITECTURE.md` (read both). Implementation lives in `apps/macos/Sources/Unison/Views/DesignSystem.swift` (tokens + shared components), `Views/Styles.swift` (rows, icon buttons, `pressScale`, `glassPanel`) and `Theme.swift` (`Motion`, colours). **If a rule here and the code disagree, fix the code or amend this file in the same change.**

Goal: a native macOS app that looks as if one designer drew every surface in one afternoon. Consistency beats local cleverness. When in doubt, copy the closest existing surface.

## 0. Process rules
1. Before writing UI, read this file and `DesignSystem.swift`. Reuse a component; if none fits, add one *there* (not inline) and document it here.
2. Never hard-code a radius, spacing step, hover opacity or animation curve in a view. Use the tokens below.
3. **AppKit follows the same tokens**: `layer?.cornerRadius = Radius.*` (never a number above 2), semantic or `Theme` colours, `Motion.*` for animation. The audit enforces radii, click-point popover anchors, font-size literals (container-relative text uses `Font.uiScaled`), `NSColor(red:/white:/srgbRed:)` literals (colours live in `Theme`) and the SwiftUI patterns.
3b. Same job, same component: every popover is a `PanelScaffold`, every text/label button is `.action(...)`, every input is `.fieldSurface()`. A reviewer should be able to grep for violations (`cornerRadius: <number>`, `.borderedProminent`, `.roundedBorder`, `ContentUnavailableView` in a panel, `.glassProminent`, a `glassPanel` with its own header/rows in a composer popup).
4. No skeleton or placeholder UI. Paint real, known content immediately and fill in the rest; loading is a small centred spinner in the panel body.
4b. Details are binding too: `docs/UX.md` 5d (no floating element crossing a neighbour, no unexplained space, concentric highlights, pointer on every clickable run, interface size through `UIScale`).
5. Verify visually: build with `UNISON_DEVTOOLS=1`, snapshot with DevTools (`snapall`, `fullprofile dm`, `settings`) in light **and** dark, and run `heightcheck` after any transcript-row change (must be 0 mismatches).

## 1. Tokens
| Token | Value | Use |
|---|---|---|
| `Radius.control` | 8 | buttons, fields, list rows, picker cells, hover-bar buttons |
| `Radius.card` | 12 | grouped sections inside panels, thumbnails, embeds, tiles |
| `Radius.panel` | 16 | popovers, floating panels, sheets, suggestion popup, the search panel |
| `Capsule` | - | tags, role chips, badges, status pills (never a number) |
| `Space.xs/s/m/l/xl` | 4/8/12/16/24 | all padding and stack spacing; panel edge padding is `l`, list inset is 6 |
Nested rule: `inner = outer - inset` (panel 16 with 8 inset holds `control` 8). Always `style: .continuous`.

Interface size: every size below is multiplied by `UIScale` (Settings, Layout; ⌘+ ⌘- ⌘0), through the tokens or `UIScale.s(...)` in AppKit; never use a bare number for a font size.

Type (system font only; use `Font.uiNano` 8 / `uiMicro` 10 / `uiCaption` 11.5 / `uiSmall` 12.5 / `uiBody` 13 / `uiTitle` 13 semibold / `uiHeading` 15 semibold / `uiLead` 17 / `uiDisplay` 22 bold, never `.caption`/`.headline`/`.title` and never `.system(size:)` literals; other weights are `.uiBody.weight(.medium)`, monospace is `.uiBody.monospaced()`; the numbers below are the nearest token):  panel/section title 13 semibold; body 13 (transcript body `Theme.bodySize`); secondary 12 `.secondary`; caption 11-11.5; `SectionLabel` 11 semibold uppercase `.secondary`; profile name 18 (card) / 22 (full). Numbers that change use `.monospacedDigit()`.

Quiet fills (placeholder discs, field-like buttons, chips) are `Fill.quiet` (`Color.primary` at 0.07), never `.quaternary`, `.tertiary` or `.quinary` as a shape fill: those are vibrant styles that blend with what is behind them, and in a surface that is composited while it moves (the sliding sidebar glass) they lose their backdrop and draw black (the sidebar search field flashed black on every toggle). The audit rejects them as `.fill(...)`/`.background(...)`.

Colour: use semantic colours (`.primary/.secondary/.tertiary`, `.accentColor`, `.background`). Fills are `Color.primary.opacity(...)`: rest 0.05-0.07 (cards, secondary buttons, fields), hover 0.07-0.11, pressed 0.12-0.15, selected row 0.10. Accent is only for the one primary action, focus rings and unread/ link affordances. Red is for destructive actions only.

## 2. Interaction (the "feel" rules)
- **Hover** = background fade via `Motion.hover` (0.12 s ease-out) and the tint steps above. No movement, no size change, no bounce on hover (emoji picker cells are the only lift, 1.1x).
- **Press** = uniform scale about the centre through `pressScale` (`Motion.pressDown/pressUp`). Never offset, never non-uniform. Apply it before `contentShape`/`onHover`.
- **Text hover**: in message text, links (blue, with a blue underline on hover: `RichTextRenderer.linkAttributes` / `linkHover`, UX.md 5d.23) underline and mention/command pills fill with the accent (role pills deepen their own tint) while hovered; clickable names (author, file) underline. Only colour and underline change, never size or weight, so text never re-wraps. Every clickable run has a pointing-hand cursor and does what the official client does (user -> profile card, role -> role card, channel/message link -> navigate, custom emoji -> emoji card, `/command` -> fills the composer). Timestamps carry the full date as a tooltip.
- **Composer text** is styled as what it will become (bold, italic, code, headings, quotes) with the markers dimmed, never hidden: the box always holds exactly what is sent. Which ranges get which style is the core's (`composer_styles`); the shell only maps styles to fonts and colours. Pills keep their own look.
- **Reactions**: a chip (28 pt, 20 pt emoji, 13 pt count) toggles your reaction at once (the core applies it and takes it back if Discord refuses), hovering for 0.25 s (`ReactionHover.delay`) shows a card with the emoji and its `:code:` side by side and the people under them ("A, B, C and 9 others", core `reaction_who` / `reaction_names_line`; a `RowButtonStyle` row with a chevron, never an underline; it stays while the pointer is on the chip or the card), clicking the card (or right-click, See Who Reacted) opens the viewer: every reaction on the message down the left, the people for the chosen one on the right (`ReactionViewer`); right-click also offers Remove My Reaction, and a trailing add-reaction chip (only when the user may react: `MessageItem.can_react`) opens the picker. Its width is part of the row height (`ReactionsRow.addWidth` in `RowHeights`).
- **Popovers open beside what opened them, never on top of it.** Anchor to the element's own rect (a mention's line rect, the chip, the avatar), not to the click point; AppKit then picks a side that doesn't cover it. Text runs use `MessageText.runRect`.
- **Pointer**: every clickable thing uses `.pointerStyle(.link)` (AppKit: `PointerButton`).
- **Hit area** = the full visible shape (`contentShape`).
- Anything that opens a menu/popover must re-sync its hover state when it closes (AppKit tracking loops swallow exit events; see `ToolbarIconButton.syncHover`).
- Reduce Motion: use `Motion.reduce` / `Motion.or(...)`; state changes still happen, motion does not.
- Disabled = 0.45 opacity, no hover.
- Keyboard: every action reachable by keyboard; Esc closes the top-most transient surface; Return triggers the default action; menus and popups show shortcuts where space allows.

## 2b. Motion constitution (binding; nothing may jump)
The rule of motion is **predictability**: after any gesture the user can say where every element came from and where it went. Anything else is a bug.
1. **Switching is a swap, not a transition** (the transcript included: no cross-fade on a channel switch; only messages arriving into an empty transcript fade in). Changing which server, DM, channel, account, tab or pane is shown replaces content in place. Rows, icons, headers and panes never slide, resize, reorder, scale or fly in. State changes that select something go through `Motion.swap { ... }` (a transaction with no animation); never `withAnimation` around a selection or a list/data replacement.
2. **Only marks animate on a switch**, and only in place, scoped to the one property: row selection fill, rail indicator height, avatar emphasis, icon corner morph. Use `.animation(Motion.select, value: <that value>)` on the mark itself, never on a container (a container-level `.animation(value:)` animates every layout change under it, which is how lists start dancing).
3. **One curve family.** `Motion.select` (0.14 s ease-out) for marks, `Motion.hover` for hover, `Motion.expand` (critically damped spring) for content that grows or collapses (folders, categories, banners), `Motion.sheet` for surfaces entering and leaving, `Motion.zoom` for a picture zooming in the viewer (UX.md 5d.32). **No spring below damping 1.0 for anything that changes layout**; the only overshoot allowed is `pressUp` (a uniform scale of the pressed control itself).
4. **Layout is stable.** An element's frame never depends on selected, hover or active state (a hint shown only on the selected row sits in a reserved slot and fades by opacity, UX.md 5d.14) (a selected avatar is not 36 pt while its neighbours are 28 pt; scale the drawn content inside a fixed slot instead). Neighbours must not move when a mark changes. Indicators are per-element and grow in place; never use `matchedGeometryEffect` to fly one between list items.
5. **Transitions are opacity only** for content (`.transition(.opacity)`); `.move` is reserved for edge-attached surfaces (banners, call stage, toasts) that enter from their own edge and start hidden behind it. Never for anything that floats over other content (jump to present, bars above the composer): sliding it over the composer is the overlap this rule prevents (UX.md 5d). No scale transitions on content, no offsets.
6. **New lists:** rows have stable ids; insertion/removal fades (`.opacity`) and the rest closes up with `Motion.expand`. A list that is replaced wholesale (different server/DM) swaps instantly.
7. **Reduce Motion:** `Motion.or(...)` or `Motion.reduce ? nil : ...` on every animation; state changes still happen.
8a. **The one deliberate shake.** A settings window refusing to close with unsaved changes swings its unsaved bar side to side (`ShakeEffect`, `Motion.shake`, 0.3 s, a count-driven offset that is zero at rest and with Reduce Motion). It is feedback to a refused gesture, not navigation, so it is the only motion allowed to move a bar sideways; UX.md 5d.37.
8. **Surfaces that enter or leave move continuously; the transcript's width changes in one step.** A pane, column, sheet or popover never pops: it slides or fades over one curve, the same both ways, and a toggle mid-flight reverses it from where it is. The transcript's width is never animated (the message list re-wraps per frame: shimmer, dropped frames, a slide that stalls then jumps): the chat claims or releases the space in one step at the moment of the gesture, and the surface moves over it on a backdrop in the chat's colour, so no empty strip shows and nothing moves after the slide ends.
   - Member list: a `Dock` on the window's trailing edge (UX.md 4.7): its width is one animated value we own, `Motion.sheet`; the column keeps its own width attached to the moving edge, so it slides in from the window edge, and the chat slot gives up or takes back exactly that width every frame (composer and transcript follow it live, text re-wrapping progressively like any window resize). Only the user's toggle slides it; a server/DM switch that hides or shows it is a swap (2b.1).
   - Sidebar: the same `Dock` (`DesignSystem.swift`) on the leading edge, hosting `SidebarColumn` (`ServerRail` + `Sidebar`). There is no `NavigationSplitView`: the system's collapse animation could not be driven (a 30-45 ms stall before the first frame, no reversing mid-flight, a final frame that could snap). We own the width: one value, `Motion.sheet`, retargeted from where it is by a further toggle (no queue, no snap); Reduce Motion swaps. The sidebar is the window's own material (glass); the dock content stays mounted while closed (scroll position survives) and slides attached to its trailing edge. The server name in the sidebar header is a `Control.standard` row that opens the server's menu (`ServerNameMenu`), built exactly like the account row in the footer: `Menu` + `.menuStyle(.button)` + `RowButtonStyle` + `.menuIndicator(.hidden)`, so it has the system's menu material and the inset every sidebar row has (`Grid.inset` + `Grid.rowPadding`; never add padding of your own inside a `RowButtonStyle` label). It is the same height as the plain "Direct Messages" title so nothing below it moves, and `.help` shows the whole name. The menu is `GuildMenu`, the one definition shared with the rail icon's right-click menu, grouped like the official client's (Invite People, Server Settings; Create Channel, Create Category; Mark as Read, Notification Settings; Move Out of Folder, Copy; Leave Server). A menu is a system menu, never a hand-built popover of rows: a popover uses a different material from every other menu in the app, and its rows were hand-styled. The toolbar toggle (leading item next to the traffic lights, where it stays), the View menu item and ⌃⌘S are one call, `AppModel.toggleSidebar()`. Open/closed is remembered across launches (`sidebarOpen`, UI-only, `UserDefaults`); the width (min 312, ideal 328, max 420) is dragged at the pane's trailing edge and remembered (`sidebarColumnWidth`, UI-only). The title and subtitle are drawn by `ChatTitle` inside the chat slot (so they follow the sidebar's live edge, and wait beside the toolbar toggle when it is shut); the window keeps the real title for the system. The search field is a toolbar button that opens `SearchPane` (it owns its field): the system search field expanded to 300+ pt once there was no system title and ate the title's room. Any pane with a real minimum width (Friends) is checked with `insetcheck` after touching the layout.
   - Never `.inspector`. Verify with DevTools `kymo sidebar|members|click:X:Y NAME [REVERSE_TICK]` (per-tick column positions and real window pixels: monotonic, eased, no plateau, no jump at the end) and `inspectorloop N` / `sidebarloop N` (dropped-frame counts), and judge by eye: `screencapture -v -l<window id>` of the offline instance (window-only capture, unaffected by other windows), ffmpeg scene scores, a contact sheet of the moving frames (see HANDOFF).
9. **Reordering** (rail and channel list): the core owns what a drop does (`rail_drop_zones`, `channel_drop_zones`/`channel_drop_plan`), the shell only shows it. Channels and categories are draggable when `ChannelItem.can_move`; over a row the pointer picks before/after (an insertion bar between rows, no row resizes) or onto a category (accent ring).  while dragging, the target shows an insertion bar (before/after) or a ring (onto a server or folder); the core says which zones exist (`rail_drop_zones`) and what a drop does. After the drop, entries slide to their new places with `Motion.expand`. Saves are debounced in the core.
10. **Accounts are rail icons.** An account is a 44 pt `RailIcon` like a server (same pill, corner morph, mention badge, 8 pt rhythm); the active one is "selected". Switching is a swap: the pill moves, the content cross-fades, nothing resizes. A missing picture shows the initial (`AccountAvatar`), never an empty disc. Add account and sign out live in the account menu, not as rail buttons. On a switch the account's pill moves at the click (`switchingTo`), the old account fades out (`Motion.veilOut`, 0.14 s), the new one is swapped in unseen, then fades in as a gentle cascade: the rail's servers, the sidebar 50 ms later, the chat 50 ms after that (`Motion.veil(_, step:)`, `veilIn` 0.28 s). Opacity only; the accounts above stay. Anything that continues in the new account (an `open` from a notification or search) runs after the swap (`switchAccount(_:then:)`). Only the latest switch continues (a generation counter), so quick ⌃1 ⌃2 never shows a half swap. Switching away from a call asks first and leaves it; the engine keeps one call at a time across accounts (`Engine::leave_other_calls` on every join). Nothing under the veil animates (UX.md 5d.17).
12. **A message arrives in one beat** (`Motion.arrival`, 0.24 s ease-out; AppKit `arrivalSeconds`, `arrivalProgress`). Your own send arrives the same way: the local echo is an insert (`MessageInserted` with id 0) and the confirmed message replaces it in place (`sameRows`), never a reload. When the reader is at the bottom, the row fades in with the table's own `.effectFade` (never `.slideUp`/`.slideDown`; a fade on a row view made off screen was lost when the table re-tiled) while the transcript glides up by its height. The glide is driven frame by frame on the display link (`ArrivalGlide`; an animated clip-view origin landed at the end at once), the scroll is claimed before the row is inserted (or `documentResized` pins the end first and the arrival is a jump), a burst retargets from where the glide is, and a scroll by the reader stops it. Verify by frames: DevTools `pretendactive on`, `fillmsgs 30`, `arrive TEXT`, `snapseq arr 0 50 100 150 200 300`. Reduce Motion keeps the fade and jumps; an inactive window swaps; a reader scrolled up sees nothing move (UX.md 5.2). The typing line is the first row inside the composer's card (UX.md 5d.15): it eases in and out with `Motion.expand` (its last names stay while it fades, the dots pause), the card grows and the chat follows its top edge; when the typed message lands, the row leaves on the same beat the message arrives. Deleted messages disappear in one step.
12c. **Presence has one palette and one dot.** Online, idle, do not disturb and offline (invisible reads as offline) are `Theme.statusOnline/Idle/Dnd/Offline` (Discord's own greens, ambers and reds), drawn by `StatusDot` everywhere (lists, member rows, DMs, profile). Never `.green`/`.yellow`/`.red`. On a profile avatar the dot sits on the rim at 45 degrees and the picture is cut away around it, and the banner is cut away around the avatar's ring (`AvatarHole`): a ring painted in a guessed surface colour never matches glass and showed as a grey halo bleeding into the picture. Any new surface that overlaps a picture with a ring cuts the gap out of what is behind it.
12a. **Summoned panels dim the window with one `Scrim`** (`DesignSystem.swift`: 50% black in dark, 30% in light; a click on it dismisses). The search panel and `ModalOverlay` (full profile, any later panel) both use it; never a hand-written `Color.black.opacity` backdrop (it was 12% and could not be seen on a dark window).
12b. **A send arrives complete.** The local echo of a reply, a send with a picture or a mention is the final row (reply line included), so the arrival glide of 2b.12 is the only motion and nothing is added when Discord confirms it (UX.md 5.6, 4.9). **A jump scrolls only when it must** (UX.md 5.7): a message already comfortably on screen is flashed in place, otherwise it is centred within the part of the viewport not covered by the toolbar and composer, and never past the transcript's ends; the flash (1.2 s fade of the accent tint) is the same either way.
13. **Unread counts ease in and out** (`BadgeSlot`, `Motion.badge`, critically damped). A count is a mark: when it becomes non-zero it fades in from 0.6 scale about its own centre, and it fades back out when it clears (Reduce Motion: fade only), so a count never pops, including when an account switch moves it from the account icon to the Direct Messages icon. Every call site shows a count through `BadgeSlot`, never `if n > 0 { Badge(...) }`.
11. **Verify:** switch server -> server, server -> Home, DM -> DM, channel -> channel, account -> account with the window at normal and slow-mo (hold the mouse; screen-record) and confirm nothing but the marks moves. Grep gate: no `withAnimation` in `selectGuild/selectChannel/selectHome/switchAccount`, no `matchedGeometryEffect`, no `.animation(` on a `ScrollView` or `List`.

## 2e. Overlays own the pointer (binding)
While anything covers the window's content (the search panel, the lightbox, a SwiftUI overlay, a call band over a row), nothing under it reacts to the pointer. AppKit views track the mouse on their own and keep doing so under a SwiftUI overlay in the same window, so every AppKit hover owner (transcript rows and the hover bar, message text links and pills, names, reaction chips, the add-reaction chip) checks `isUncovered(at:)` (`DesignSystem.swift`: a hit test from the window's content view) before it lights up, and clears its hover when it is covered. A new AppKit view that tracks the mouse uses the same check. Popovers are their own windows and need nothing.
`isUncovered` hit-tests from the window's frame view (`contentView.superview`): `NSView.hitTest` takes a point in the view's superview, and the content view is flipped, so converting into the content view mirrored the point vertically and found some other view (names never underlined, the row's hover bar flickered). DevTools `namehit` sends a pointer move through the transcript's own mouse path to every visible author name and logs whether it underlined.

## 2c. No system focus rings (binding)
macOS draws a blue box around whichever control holds keyboard focus whenever Full Keyboard Access is on (System Settings > Keyboard), and it does so in every hosting root that has not switched it off. Unison never shows them: our controls show their own state (hover and press fills, the accent ring on text fields, `ProgressBar`, selection fills), so the box is only noise and looks like a bug.
1. Every SwiftUI tree gets `.noFocusRing()` (`focusEffectDisabled`): the main window and Settings roots in `UnisonApp`, and anything hosted from AppKit (popovers, overlays) through `hostedController` / `hostedView`, never a bare `NSHostingController(rootView:)`. SwiftUI inherits it down a tree but not across a popover, a separate scene or an AppKit host.
2. An AppKit control subclass sets `focusRingType = .none` (`PointerButton` does; build on it).
3. The audit fails on a bare hosting root, an `NSButton`-family subclass without it, and a scene root missing it. To check by eye with Full Keyboard Access on: dev command `tabkey` after opening a surface (e.g. `profilegallery wide card`) moves focus like Tab, then snapshot.

## 2d. Glass and edges (binding)
Every surface that scrolls under the toolbar or a header gets the **same edge treatment**, so the left pane's header and the chat's header look like one material: SwiftUI scroll views and lists use `.scrollEdgeEffectStyle(.soft, for: .vertical)`; the AppKit transcript gets the same through its hosting `MessageList` (ChatPane). Floating glass (composer, popups, switcher) uses `glassPanel(cornerRadius:)` only, never a hand-tuned material, tint or blur. A new scroll surface under a header copies one of the existing ones.
**Glass on the left, flat theme colour everywhere else (the Claude desktop layout).** The rail and the sidebar are the system's glass; everything to the right of them (the chat, its header strip, the member column, the slide backdrops) is the one flat theme colour `Theme.chatBackground`, dark or light. The window toolbar draws no background of its own (`.chatHeaderColour()` in `ChatPane`): the strip over the sidebar is therefore the sidebar's glass, never an opaque band, and the strip over the chat is that same flat colour because `ChatBackdrop` (in `SteadySidebarInset`, permanent, from the sidebar's live edge to the window's, extended up under the toolbar) sits behind it. A hairline (`.separator` at 0.5) runs under the header over the chat and the member column. One component paints the pane: `ChatBackdrop`; never hand-paint `chatBackground` over the chat from a new view. A frosted chat was tried and removed: the transcript is an AppKit scroll view that paints its own opaque background, and a see-through chat made the header and the pane two different materials.
**Account avatars share one placeholder.** Wherever an account's own picture is shown (rail, self row, member row of yourself, settings, account lists) the placeholder under it is `AvatarInitial(name:side:)`, the first letter on a soft disc, so a transparent picture looks the same in all of them.
**Avatars are backed.** Every avatar draws its placeholder disc underneath the picture (`RemoteImage(..., backed: true)`), so a transparent or empty image still shows a disc, never a hole. Server icons, emoji and stickers are not backed (transparent on purpose).
Verify by eye: dev command `snap` in light and dark; the header strip over the chat is the same colour as the chat body, with no visible seam.

## 3. Components (use these)
- **Control heights**: `Control.standard` (32) in sheets and forms, `Control.compact` (28) in bars, headers, panel accessories and list rows (same height as `IconButtonStyle`, so mixed lines align). Never another number; `scripts/ui-audit.py` enforces it.
- **Notice bar**: `NoticeBar(symbol:, text:, action:)` is the one non-modal bar above the composer (one line, at most one `primary` action), e.g. "You haven't joined this thread" + Join thread. Do not hand-build another.
- **Settings window** (`SettingsChrome` in `Views/SettingsChrome.swift`): the one chrome for User Settings and Server Settings: glass sidebar of `SettingsGroup`s, a 52 pt header strip with the pane title and the full-width rule, the flat pane, the unsaved bar, and the close guard (UX.md 5d.37). Never hand-build another settings window.
- **Settings pages** (`SettingsPage`, `SettingsList` + `SettingsRow`, `SettingsSearch`, `SettingsEmpty`, all in `SettingsChrome.swift`): every page of a settings window is a `SettingsPage` (one centred column up to 600 pt, a one-line description under the header title), lists are rows in one `SettingsList` card (a `.groupCard(padding: 0)`) with hairlines, each row `Grid.personRow` high; a row that opens something is `interactive` and holds a `RowButtonStyle` button (hover fill, pointer), never `.tile`, a long list has a `SettingsSearch` above it (beside its one primary action, `Control.standard`), and a list with nothing in it is a `SettingsEmpty` centred in the room, never the top-left corner. This is the official client's page structure; copy it for any new settings page.
- **Unsaved bar**: `UnsavedBar(saving:reset:save:)`, the one save control of a settings surface (User Settings and Server Settings): "You have unsaved changes", Reset (`secondary`) and Save Changes (`primary`, ⌘S) in a `glassPanel(Radius.panel)` at the foot of the pane, shown with `.safeAreaInset(edge: .bottom)` and an opacity transition only while something differs from what is saved; the content above gives it room, nothing underneath moves sideways. Never a Save button inside a pane (UX.md 5d.34).
- **Buttons**: `.buttonStyle(.action(.primary|.secondary|.destructive, fill:, height:))`: 32 pt, `Radius.control`. One `primary` per surface. Icon-only chrome buttons: `IconButtonStyle` (28 pt circle). Row-like buttons: `RowButtonStyle`. Hover-bar buttons: `ToolbarIconButton` (same hover steps as above). The sidebar footer's update strip (`UpdateStrip`) is one `Control.compact` chip in the sidebar's content edges, in a row of its own above the account row, so the picture, mute, deafen and settings never move or squeeze the name. It appears only when there is something to act on and its words say what it is (Update available, Restart to update, Update failed, retry). The whole chip is the button and its hover and press change that same shape (never `RowButtonStyle`, whose row fill is wider than a chip). One indicator at a time: a download with a known length fills the chip itself from the left; work with no length (checking, installing, restarting) shows a small spinner in the icon's place; never a ring and a bar together. A click while it works opens a popover with the same `UpdateProgressCard` that Settings, Updates draws. The footer grows upward when it appears (the list gives way on `Motion.expand`; Reduce Motion: at once); its words and icon cross-fade as the update moves on and its size never changes. DevTools `updatestage available|downloading|installing|ready|waiting` shows each stage, `updatesim` is a click-through (including the Keychain popup). DevTools `updatestage available|downloading|installing|ready|waiting` shows each stage offline.
- **Inputs**: `TextField(...).fieldSurface()` (34 pt, filled, accent ring on focus); a multi-line text area is `.fieldSurface(multiline: true)` with `axis: .vertical` and a `lineLimit` (grows from one field high), never the fixed row. Never `.roundedBorder`.
- **Panels / popovers**: `PanelScaffold(title:count:width:accessory:)` + `PanelBody(state:)`. Title bar 44 pt, `Divider`, body. States: `.loading` (small centred spinner), `.empty(symbol,title,message)` (`EmptyState`), `.rows` (lazy scrolling list, height clamps 80...480). Loading and empty share one minimum height (220) so panels never jump. Width 400 for lists, 320 for the profile card. Popover arrow edge: toolbar items `.bottom`, side lists `.leading/.trailing`, composer `.top`.
- **Popovers anchored in scrolling content** (profile, role, emoji, who-reacted, reaction picker, member and DM rows): AppKit ones are opened only through `AnchoredPopover.show` (one at a time, transient), SwiftUI ones carry `.dismissesPopoverOnScroll($shown)`. Both close as soon as less than half of the anchor is inside the visible part of its scroll view (under the toolbar or the composer counts as gone). Never `NSPopover()` directly (audit).
- **Text hit testing** (`MessageText`): pointer position, cursor rects and popover anchors for text runs all go through the cell's own text rectangle (`toText`/`fromText`), never hand-offset assumptions. Check with DevTools `hovercheck` (draws a hovered pill in fields of different shapes and compares pixels with the hit test; must report all fields agree).
- **Header buttons** (window-toolbar items: the sidebar toggle, a forum's back button, the trailing group of call, pins, saved, threads, inbox, members and search, and any added later): the system's own toolbar button with its Liquid Glass circle or capsule, never a hand-drawn imitation. Our own `IconButtonStyle` inside the glass made the whole capsule shimmer when clicked, and hiding the shared glass left a bare icon. Popovers from these buttons go through `.toolbarPopover(isPresented:)` (AnchoredPopover, AppKit), never SwiftUI's `.popover`: with it the button's glass flipped between its pressed and hover circles every frame while the popover was open (found in a screen recording). Known and accepted: on the flat dark chat colour the system's pressed state draws a dark circle for the length of the press.
- **Header popup icons** (Pins, Saved, Threads, Inbox): `ContentDotIcon(symbol:dot:)`. A small neutral dot (6 pt, primary at 0.55, never accent or red; those belong to unread and mentions) shows when the core says the popup has something in it (`header_dots` -> `HeaderDots`, from data already held, no request). Pins follow the channel's last-pin stamp (it can stay set after the last pin is removed), Saved the local list, Threads a known unarchived thread under the channel, Inbox the Unreads tab (Mentions is fetched on open). A new header popup adds a field to `HeaderDots` and uses this component; never overlay a hand-made dot.
- **Message text outside the transcript** (replies, Inbox, Saved, Search, quick switcher, forum cards, notifications): comes from the core already resolved (`preview_text` for one-line plain text, `RichText` + `PinText.make` where pills are wanted, as in the Inbox mentions). A shell never shows `content` raw; a raw `<@123>` or `<@&123>` on screen is a bug. A role I hold is marked like a mention of me (`RoleMention.is_me`: yellow wash), and a message that pings me, by name, @everyone or a role (`Store::pings_me`, which finds the server through the message's channel when a REST page gave none: UX.md 5d.36), gets the mention row highlight.
- **Unread mention count**: always `Badge(count:)`, never a hand-made red capsule. Its look is the user's choice (Settings, Layout: Red count, Subtle count, Hidden; `BadgePrefs`, UI-only).
- **Grouped content**: `.groupCard()` (soft 12 pt card). Labels above content: `SectionLabel`.
- **Profile**: `ProfileBanner` + `ProfileAvatar` + `ProfileNames` + `RoleChip` are shared by the card and the full profile; change them, not the call sites.
- **Word lists** (`WordChips`): a short list the person keeps (notification keywords) is removable chips above one `fieldSurface` input; Return or a comma adds, the x removes. The core normalises, limits and de-duplicates and returns its one-line refusal, which shows under the field until the next keystroke. Never a comma-separated text field.
- **Search panel** (`FindPalette`, ⌘K and ⌘F): the only search surface; there is no second popover or field. Field (52 pt row, 17 pt text `uiLead`, icon and text start where a result row's content starts: list inset `Space.s` + row padding `Space.m`), scope tabs (`ScopeTabs`: quiet text tabs, the chosen one in a soft capsule at 0.09, 24 pt, each pill lines up with the rows' highlights; none when there is one scope; Tab and ⌘1 to ⌘3 switch, the tooltip names the number; never a `TabBar` here), grouped list (`SectionLabel` headers, 44 pt place rows, message rows with a 28 pt avatar, the searched words in `HighlightedText`, shortcut hints in `KeyCap`), footer of hints. Status lines are one small row, never a skeleton: cached results first, then a spinner row while Discord answers, then "nothing found", then an error with its next step and a retry row. It eases in (a 0.32 s critically damped settle from 0.97 and a fade, `Motion.sheet`) and out (a 0.1 s fade); it is always mounted so it can leave as well as arrive, and Reduce Motion swaps. Highlight ranges come from the core.
- **Call view** (`CallView` in `Views/Voice.swift`, `VideoStage`/`VideoTile`/`PersonTile`/`TileMarks` in `Views/VideoViews.swift`; which one shows is `AppModel.openCall`/`callPane`, one rule). Where it sits follows the official client:
  - **Server voice channel**: the call takes the chat pane and the channel's own chat is a column on the trailing edge, a `Dock` like the member list (toggled from the bar, remembered in `callChatOpen`); the member list steps aside. The call never gets less than `CallView.minWidth` (440): the column opens only when both fit (`chatFits`, a pane of 700+), and is about a third of the pane within 260...360. Narrower, the chat stays shut and its toggle says to widen the window.
  - **DM or group DM**: the call is a band above the conversation, in the flow, so it never covers a message and the transcript keeps its full width. Drag its bottom edge to resize it (`PaneResizeHandle`, the same handle as the sidebar and member column; remembered in `callBandHeight`); it is at least 200 and always leaves the conversation 260.
  - **Never pushes**: the stage draws into a plain filler and is told its size (`VideoStage.size`, measured by `CallView`, never by the stage itself; a frame reports its child's size when the child is wider, which once froze tiles at their old size after a window shrank). The view is clipped to its frame. The bar switches to compact buttons and drops the connection details below `minWidth`. Check every change at 1600x1000, at the 900x560 minimum and back (DevTools `fakecall N` in a DM and in a server channel, then `resize`).
  - Its backdrop is `Theme.callStage` (dark in both appearances) and stops at the header (`ignoresSafeAreaEdges: []`), so the strip over the chat stays the chat's colour (2d).
  - **Tiles**: everyone has one tile with a stable id (`member/<id>`, whatever they show): a picture when they send one (turned upright by `VideoOrientation`, fitted on `Theme.mediaBackdrop`, so a portrait phone shows whole between bars), their avatar centred otherwise; someone being rung is a dimmed tile with "Ringing…". Order: streams (or a Watch card), then members, then who is rung. The stage keeps one view per tile and only positions them: `VideoStage.layout` is a pure function from items, room and mode to rectangles, so a layout change never moves a video layer to a new host (that is how feeds vanished). Modes (`VideoStage.mode`):
    - **Grid** (default): fills the room. The column count with the most area per tile (more columns win within 15%), each cell as large as the room allows with a shape between 1:1 and 2:1, rows centred. Two people share the space; nobody is shrunk into a strip because one other person exists.
    - **Picture-in-picture**: exactly two people and both have a picture: one fills the stage, the other is an inset (24% of the width, 120...280, `Space.s` from the corner, `Radius.control`, no name). Clicking the inset swaps them, like FaceTime.
    - **Focus**: three or more tiles and one clicked: it fills the room above a strip of the rest; clicking it again goes back. A stream that starts is focused once (three or more tiles only) unless you focused a tile yourself.
    - A focus or swap is forgotten when the stage falls back to the grid, so a stale choice never focuses someone later. Clicks that would do nothing (a two-person grid, the big tile in PiP) are disabled. Focus and swaps are swaps (2b.1); tiles arriving or leaving fade and the rest move with `Motion.expand`; a resize follows the window live. Check layouts with DevTools `stagecheck` (120 states and sizes: every tile placed, inside, no overlaps but the inset, no wasted room) and in place with `fakecall`.
  - **State on the tile, never moving it**: the green speaking ring (`Motion.select`), the mute or deafen glyph bottom-trailing (red when a moderator did it), the name capsule bottom-leading (`TileName`, LIVE for streams).
  - **One bar** under the stage: connection on the leading side, mute, deafen, camera, share and a solid red disconnect centred, the chat toggle trailing (pane only). Your camera and screen share follow the call, never the view. Standalone preview: DevTools `callgallery N [speak] [mute] [stream] [WxH]`.
- **Server card** (`ServerCardView`, `ServerTagPopover`, `TagChip`): a server tag opens a 320 pt preview beside itself, laid out like the profile card (banner strip, icon in a ring with `Radius.card` inside `Radius.panel`, name `uiHeading`, the tag chip, member count, three lines of description, Open Server as the one primary action). AppKit tags use `AnchoredPopover`, SwiftUI ones a popover with `.dismissesPopoverOnScroll`. Preview with DevTools `servercard N|unknown`.
- **Pane resize** (`PaneResizeHandle` in `DesignSystem.swift`): the one drag handle for a pane's edge (sidebar, member column, a DM's call band): an 8 pt strip wider than it looks, the column or row resize pointer, translation since the drag began. Never hand-build another.
- **Floating surfaces** (the search panel, composer, suggestion popup, call overlays): `glassPanel(cornerRadius: Radius.panel)`.
- **Popovers opened from a context-menu entry** (Profile on a friend, member or DM row) anchor to the row that was right-clicked, never to the window or the menu item: `ContextClick` remembers the last right click and `ProfilePopover.showAtContextClick` uses it. The overlay's content is clipped to the panel's rounded shape, so a banner image follows the corners.
- **Full profile** is a `ModalOverlay` (`DesignSystem.swift`, mounted in `MainView` beside `FindPalette`), not a system sheet: the search panel's enter and leave, a dimmed backdrop that closes on click, Esc closes.
- **Sheets/modals**: fixed width (440 add-account, 560 full profile), content padded `Space.xl`, actions bottom-right (`secondary` Cancel then `primary`), Esc cancels, Return confirms. `ChoiceBar` (the `TabBar` look) for mode switches, never a system segmented `Picker` and not link buttons.
- **Composer suggestion popups** (mentions, channels, emoji, slash commands, anything added later): one `SuggestionPopup` with `SuggestionRow` rows. Callers pass only content (leading glyph, title, detail, trailing caption); header, 8 pt padding, 36 pt rows, 0.10 selection fill and the shortcut hint belong to the component. Never hand-build a popup or size/pad its rows in a feature file.
- **Custom-surface buttons** (media tiles, cards, chips, avatars): `.buttonStyle(.tile)` (press scale + pointer). Never `.plain`.
- **File drops**: `.fileDrop(enabled:label:perform:)` on the whole pane (chat). It shows one centred "Drop to upload to …" card while files hover; AppKit text views must not register file types themselves (`ComposerNSTextView.updateDragTypeRegistration`), or they swallow the drop. Dropped URLs go through `ComposerBus.attach`.
- **Sending progress**: `SendProgressRow` (title, detail, `ProgressBar`, Cancel) above the composer for a message that is being shrunk, uploaded or handed to Discord; one row per send, same width with or without Cancel. `ProgressBar(fraction: nil)` sweeps for work of unknown length. A cancelled send, or a failed one when the draft is empty, comes back into the composer by itself with the reason in the banner; otherwise `FailedSendRow` (reason, preview, Retry, Edit, discard) waits above the composer and is driven by the core's send list; errors are one plain sentence from the core (`Error::user_message`), never a status line. The character counter shows only near the limit (core rule) and turns red when over. Preview every state with the dev command `sendrows`.
- **Tabs and choices**: `TabBar(titles:selection:)` for a few views of one thing, and `ChoiceBar(options, selection:)` for choosing one of a few values (a theme, a size, Mentions or Unreads, a setting in Settings): equal widths, fills its container, selected fill 0.12, hover 0.06. There is no other segmented control: the audit rejects `.pickerStyle(.segmented)`. In a Settings form the row is `LabeledContent(label) { ChoiceBar(...).frame(width: 260) }`. Icon-only choices pass `symbols:` to `TabBar` (the permission tri-state).
- **Profile**: the banner is a fixed-height strip with the picture as an overlay, never a child that can widen the layout; the avatar and the display name open the full profile (avatar dims and says "View profile", name underlines); the full profile uses `TabBar`, group cards and `RowButtonStyle` lists, and its frame is top-leading so an overflow clips instead of shifting everything left.
- **Places a surface points at** (Inbox, Saved, Search, pins, replies, links, notifications, switcher, cards): `model.open(account:guild:channel:message:)`, never `selectChannel`/`selectGuild` from a view (UX.md 8; audit-enforced). The rail (`railReveal`: folder opened, icon scrolled in) and the sidebar (`sidebarReveal`: category opened, row scrolled in) follow any selection; a view that holds its own popover state closes it on `model.transientEpoch`.
- **Lists**: rows via `RowButtonStyle` (30 channel / 40 person / content-sized in panels), 2 pt gap, selected = 0.10 fill.
- **Empty states**: icon (26, tertiary) + 13 semibold title + 12 secondary one-liner. No `ContentUnavailableView` inside panels.
- **Scrollbars**: overlay (auto-hiding) by default (`UnisonApp.init`); opt back in with the `UnisonSystemScrollbars` default. Never draw a custom always-visible gutter. Navigation lists (the server rail, the sidebar's DM and channel lists) show no scroller at all, not even on pointer hover; content panes (the transcript, the member list, popups) keep the auto-hiding one.

## 4. Behaviour rules that are UI
- Optimistic updates; errors surface as a quiet inline message or toast, never a modal for a rate limit. Never fire a request per keystroke (typing is throttled to 1 per 8 s per channel; member search is debounced 250 ms and de-duplicated).
- Order of states in any async surface: cached content > loading spinner > empty > error with retry hint.
- Copy: sentence case, no trailing full stop on titles, one short helper line max.

## 5. Review checklist (run before every UI PR)
0. `scripts/ui-audit.py` must exit 0 (it encodes item 1 below plus spacing on the `Space.*` scale, no `.plain`, no system text styles, AppKit corner radii, click-point popover anchors and the motion rules of §2b). Anything the audit cannot see (hover, click targets, popover placement) is verified by driving the app: `pointer X Y [click]` in DevTools. The pre-commit hook runs it.
1. grep: no numeric `cornerRadius`, no `.borderedProminent/.bordered/.glass/.glassProminent/.roundedBorder`, no `ContentUnavailableView` in panels.
2. Light and dark snapshots of every changed surface, in place in the main window at a normal size and at the 900x560 minimum (and back), not only in an isolated preview. Look at what surrounds the change too: the gap above the composer, chips in rows, the rail and sidebar during an account switch (UX.md 5d.15 to 5d.17).
3. Hover, press, focus, disabled states exercised; Esc and Return work.
4. Reduce Motion on: nothing slides or scales. Motion constitution §2b walked through (switch every kind of selection; nothing but marks moves).
5. `heightcheck` 0 mismatches (system rows excepted, see HANDOFF), `cargo test --workspace` green.
